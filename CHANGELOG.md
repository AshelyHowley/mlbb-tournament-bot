# Changelog

## 1.4.0 — FINAL TOURNAMENT SYSTEM UPDATE (2026-09-23)
Полноценная турнирная система поверх существующей регистрации. Жеребьёвки/автогенерации сетки по-прежнему нет — матчи создаются вручную персоналом.
* **Формат участия**: TEAM (2-5 игроков для матча, капитан считается игроком, регистратор — нет; регистрация по-прежнему допускает 0/5 и 1/5) и SOLO (ровно 1 человек) — раздельно.
* **Серии BO5**: «матч» турнира — серия из отдельных игр («каток»); счёт/победитель серии всегда ВЫЧИСЛЯЮТСЯ из записанных игр, никогда не вводятся напрямую. Максимум 5 игр, остановка при 3 победах любой стороны, 5-я игра только при счёте 2:2, 6-й игры не бывает. Исправление ошибочно внесённой игры — ГЛАВНЫЙ АДМИН/АКТИВНЫЙ ЗАМЕСТИТЕЛЬ, до завершения серии всегда, после — только если по её результату ещё не стартовал следующий матч.
* **Полная сетка**: раунды → полуфинал → финал, плюс отдельный матч за 3-е место (тоже BO5) между проигравшими полуфиналистами. 1-е место — победитель финала, 2-е — проигравший финала, 3-е — ТОЛЬКО победитель матча за 3-е место (никогда не выводится как «4-е место»); турнир считается полностью завершённым, когда сыграны и финал, и матч за 3-е место.
* **Уведомления по результату серии** (не после каждой игры, а один раз по завершении серии) — всем реальным участникам состава обеих сторон (регистратор-без-роли исключён, капитан включён), список получателей — по фактическому составу 2-5, а не жёстко 5. Отдельно ГЛАВНЫЙ АДМИН/АКТИВНЫЙ ЗАМЕСТИТЕЛЬ может составить произвольное уведомление (текст/фото/видео/документ) с предпросмотром, подтверждением, статусом доставки по каждому получателю и повторной отправкой только неудачных — новый, отдельный от общей рассылки механизм.
* **Роли**: 👑 ГЛАВНЫЙ АДМИН (`ADMIN_TELEGRAM_ID`, без изменений) и 🛡 ЗАМЕСТИТЕЛЬ (максимум 2 одновременно) — приглашение по одноразовой криптостойкой ссылке `?start=deputy_<token>` (кандидат сначала принимает и становится ожидающим без прав, затем отдельно нужно одобрение главного админа). Заместитель получает почти все права персонала, кроме управления другими заместителями, смены главного админа и редактирования истории (она read-only для всех).
* **Завершение турнира — архивация, не удаление**: атомарно фиксирует текущий турнир как `completed` (все призовые места определены) либо `closed_early` (нет — требуется явное подтверждение словом «ЗАВЕРШИТЬ»), затем создаёт новый пустой активный турнир. Ровно один активный турнир в любой момент — обеспечено на уровне PostgreSQL (частичный уникальный индекс + блокировка строки), проверено конкурентными попытками завершения.
* **📚 История турниров** — read-only раздел для персонала: список завершённых турниров, карточка с датами/местами/составами, детализация по командам, соло-участникам, полной сетке, каждой серии и игре в ней, статистика только по реально хранимым числам (без выдуманных MVP/KDA). История — замороженный снимок на момент завершения (имена/username участников не меняются задним числом при последующих изменениях профиля).
* Новая миграция `004_tournament_system.sql` (поверх 001-003, данные сохраняются): `tournaments`, `match_games`, `deputy_invites`, `deputies`, `result_broadcasts`/`result_broadcast_deliveries`; `tournament_id` добавлен в `teams`/`team_members`/`solo_players`/`matches` с обратным заполнением в единственный активный турнир; уникальность названия команды/капитанства/соло-регистрации переведена с «когда-либо» на «в рамках турнира»; заморозка отображаемых имён (`display_username`/`display_full_name`) на момент архивации.
* Регрессия: 531 → 592 автотеста, 0 FAIL. Расширены нагрузочные тесты (10/20/50 конкурентных операций, p50/p95/max): гонки за право записать игру серии, гонки за одноразовое приглашение заместителя, гонки за завершение турнира.
* Дважды выполнен dry-run миграции 004 на реальной production-базе `mlbb_tournament` в транзакции с ROLLBACK — данные не тронуты, применение подтверждено только после прохождения всех проверок.
* `ACCESS_MODE` не менялся (остался `public`). CourierBot не затронут.

## 1.3.0  (previous: 1.2.0)
Окончательная модель ролей команды: **регистратор / капитан / участник** независимы.
* После названия команды создатель выбирает роль: «👑 Я капитан» (регистратор+капитан+участник, 1/5), «🎮 Я участник, капитан другой» (регистратор+участник, 1/5, капитан ожидается), «📝 Я только регистрирую» (0/5, в состав не входит).
* Отдельная **captain invite** ссылка `?start=captain_<token>` (192 бита CSPRNG, `UNIQUE`, формат в БД, отличается от player-токена). Принятие атомарно: токен, private-доступ, подписка, «не в другой команде», лимит 5; новый человек → member+captain, существующий member → только повышение (без второй записи и без нового места). После назначения капитана ссылка мёртвая («У этой команды уже назначен капитан»).
* Пока капитан не назначен, набор игроков по player-ссылке закрыт («Капитан пока не назначен»).
* Регистратор до назначения капитана: видит статус, получает/обновляет ссылку капитана (старая сразу недействительна), может отменить регистрацию. После назначения прав на состав не имеет (ни удалять, ни заменять, ни передавать).
* Капитан: приглашение, удаление/замена, **передача капитанства** существующему участнику (атомарно, размер не меняется; forged callback / гонки защищены блокировкой строки команды). Капитан не может удалить/покинуть себя.
* «Моя регистрация» показывает роль (Капитан / Участник / Регистратор), капитана («ожидается») и состав X/5; регистратор-только не считается игроком и может ещё зарегистрироваться соло или вступить игроком в другую команду. Обычный пользователь регистрирует одну команду, администратор — сколько угодно.
* Миграция `003_team_roles.sql` (поверх 002, данные сохраняются): `teams.created_by` (backfill = captain), `captain_id` допускает NULL, `captain_invite_token` (UNIQUE + CHECK), обновлён отложенный триггер состава (капитан назначен ⇒ ровно одна captain-строка = captain_id; капитан не назначен ⇒ captain-строк нет; всегда ≤ 5).
* `ACCESS_MODE=private` без изменений: captain- и player-ссылки не обходят закрытый режим.

## 1.2.0
Командная регистрация по пригласительной ссылке (вместо ввода 4 username):
* Капитан вводит только название → бот создаёт команду (капитан = участник №1) и выдаёт личную ссылку `https://t.me/<bot>?start=team_<token>`. Токен — 192 бита CSPRNG (`secrets.token_urlsafe(24)`), `UNIQUE` + `CHECK` формата в БД; последовательный id нигде не используется как защита.
* Игрок открывает ссылку → карточка приглашения → «Вступить» (проверки: private-доступ, токен, лимит, другая команда, эта команда, подписка). Идентификация только по Telegram `user_id`; username необязателен (NULL допустим везде, «None/@None» не показываются).
* Максимум 5 человек включая капитана — на уровне PostgreSQL: триггер `BEFORE INSERT` блокирует строку команды `FOR UPDATE` и считает состав после получения блокировки (гонки на последнее место невозможны), плюс отложенная проверка при COMMIT. `UNIQUE(user_id)` — один игрок, одна команда; частичный `UNIQUE` — один капитан; строку капитана нельзя удалить; членство нельзя «перебросить» UPDATE-ом.
* Управление составом: «Моя команда», «Пригласить игрока», «Управление составом» (заменить/удалить с подтверждением), «Покинуть команду» для участника (капитан — только через администратора). Уведомления капитану о вступлении/выходе и удалённому игроку (best-effort, без дублей).
* Deep-link не обходит `ACCESS_MODE=private` (access gate стоит раньше любых хендлеров).
* Соло-регистрация больше не требует username.
* Миграция `002_team_invites.sql` (data-preserving): старый состав архивируется в `team_members_legacy`; участники, которых можно сопоставить с аккаунтом, переносятся по `user_id`, username-only строки остаются только в архиве.
* Удалена старая механика (FSM ввода username, `UsernameTaken`, проверки по `username_norm`).

## 1.1.0
Режим закрытого тестирования:
* `ACCESS_MODE=private|public` (по умолчанию `private`; неизвестное значение — бот не стартует) и `ALLOWED_USER_IDS` (список через запятую, trim, проверка, без дублей; ошибки видны при старте).
* Глобальный `AccessMiddleware` — первый наш middleware на уровне Update, до трекинга пользователей, фильтров, FSM и хендлеров. Запрещённому пользователю отвечает «🔒 Доступ к боту ограничен»; на CallbackQuery всегда вызывается `answer()`.
* Разделены `Config.can_access_bot()` и `Config.is_bot_admin()`. Администратор бота — только `ADMIN_TELEGRAM_ID`; статус админа Telegram-чата не используется.
* Бот отвечает только в личных чатах (в чате/канале турнира молчит).

## 1.0.1
Исправления по итогам аудита и regression (каждое покрыто тестом):
* **Fix:** удаление команды, участвующей в матчах, падало необработанным `RestrictViolationError` (ON DELETE RESTRICT даёт sqlstate 23001, а не 23503) — теперь понятное сообщение.

* **Fix:** `parse_int("0")` возвращал 0.
* **Fix:** пользователь, заблокировавший бота, не «размораживался» по `/start` в пределах 5-минутного кэша трекинга.

* **Perf:** проверка занятости username в регистрации команды — 2 запроса вместо 10; пул стартует с 5 прогретых соединений.
* Убран мёртвый код и неиспользуемые импорты.
